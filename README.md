# Vault GitHub Bridge

通过 GitHub 同步 Obsidian 笔记的跨平台插件，当前版本 **0.2.1 测试版**。

笔记保持普通 Markdown 和附件格式，每台设备有本地副本，离线时可以编辑。桌面端检测到笔记库自身的 `.git` 后使用本机 Git；没有本地仓库时使用 GitHub REST API。移动端始终使用 API，不加载 Node.js，也不显示本机 Git 管理入口。面向 macOS、Windows、iOS / iPadOS、Android；真实设备兼容性还需要逐端验证。

## 安装

要求 Obsidian **1.11.5 或更新版本**，并允许使用社区插件。

### 桌面端手动安装

1. 先用小型测试笔记库验证。
2. 解压 `vault-github-bridge-0.2.1.zip`。
3. 将解压后的 `vault-github-bridge` 整个文件夹放入：

   ```text
   你的笔记库/.obsidian/plugins/vault-github-bridge/
     main.js
     manifest.json
     styles.css
   ```

   如果修改过 Obsidian 配置目录，使用实际的配置目录替代 `.obsidian`。macOS Finder 可以用 `Command + Shift + .` 显示隐藏文件夹。

4. 重启 Obsidian，在“设置 → 社区插件”中启用 **Vault GitHub Bridge**。

### 手机与 iPad

本插件通过 GitHub Release 分发测试版本，可以使用 [BRAT](https://github.com/TfTHacker/obsidian42-brat) 安装和更新：

1. 在 Obsidian 社区插件中安装并启用 BRAT。
2. 打开 BRAT 设置，添加本插件的源码仓库：`yann-su/vault-github-bridge`，选择 `0.2.1` 或最新版本。
3. 启用 Vault GitHub Bridge，在手机上配置自己的笔记仓库和 Token。
4. 新建本地笔记库后，先预览同步计划，再确认下载笔记。

手机上的 Obsidian 不会因为笔记仓库同步了就自动安装本插件。若插件源码仓库为私有，BRAT 还需要该源码仓库的只读凭据。

如果使用能访问 Obsidian 本地笔记库且显示隐藏目录的文件工具，也可以手动放置相同的三个文件；具体访问能力取决于系统。笔记仓库与插件源码发布仓库应分别管理。

## 连接笔记仓库（API 模式）

例如，笔记仓库地址为 `git@github.com:your-name/my-notes.git`，对应设置如下：

| 设置 | 填写内容 |
| --- | --- |
| GitHub 用户或组织 | `your-name` |
| 仓库名称 | `my-notes` |
| 分支 | `main`（临时测试时填测试分支） |
| 设备名称 | 例如 `MacBook`、`Windows`、`iPhone`、`iPad` |

1. 确认仓库已有至少一个提交，如 README；第一版不自动创建仓库或初始化空仓库。
2. 到 [GitHub fine-grained token 设置](https://github.com/settings/personal-access-tokens/new) 创建凭据：只选目标仓库，授予 **Contents: Read and write**。只接收更新可使用 Read-only。
3. 在插件设置的“GitHub 凭据”中创建或选择 SecretStorage 凭据。Token 需要在每台设备分别设置，不要把它写进笔记、Git 远程地址或 `data.json`，也不用在聊天里发送。
4. 填写仓库设置，点击“保存配置”，再点击“预览同步计划”。预览只读取远端，不提交文件。
5. 核对计划后点击“确认计划并同步”。先确认一台设备的结果，再接入另一台设备。
6. 确认正常后启用“自动同步”。

插件使用 HTTPS API，SSH 地址仅用于识别 owner/repo；手机不需要 SSH 密钥。私有仓库中的笔记仍以普通文件保存，当前没有端到端加密。

## 本机 Git 模式（桌面端）

笔记库根目录有 `.git` 文件或目录时自动启用，支持普通仓库和 linked worktree；不会把上级文件夹的 Git 仓库当成当前笔记库。需要已安装 **Git 2.25+**。存在 `.git` 但 Git 不可用时显示错误，可在同步设置中填写 Git 可执行文件的完整路径，不会静默改用 API 写入另一个仓库。

- 同步跟随当前本地分支的上游，使用本机 Git 凭据，不使用 API 模式中填写的仓库、分支或 Token。自动提交笔记，再 fetch、接收更新并普通 push；不强推。
- 本地和上游分叉时自动执行普通 merge，保留双方提交；不同文件、同一文件不重叠的修改可自动合并。推送期间另一台设备抢先更新时，重新获取并合并，最多尝试三次普通推送。真正的内容冲突会暂停推送，并提示进入“处理同步冲突”；同一组冲突不反复弹通知。
- 未完成的 merge / rebase / cherry-pick / revert、分离 HEAD 会阻止自动同步。合并前若暂存区仍有其他修改，需先核对提交或取消暂存，避免混入合并提交。不自动 stash；未提交文件可能被覆盖时，由 Git 停止合并。
- 自动提交仅选择同步范围内的笔记和附件，遵守 Git ignore 和大小限制；其他已暂存文件保留。大量删除先到提交面板核对具体清单。**Git 拉取遵循仓库的全部跟踪文件**，因此仓库已有的配置文件也由 Git 管理。
- “Git 仓库管理”显示当前分支、上游、远端、领先 / 落后提交数、文件状态与冲突。
- “分支管理”支持本地分支切换、新建、从历史版本建分支、跟踪远端分支、发布当前分支和用 `branch -d` 删除已合并分支。笔记有未提交修改时先提交或 stash；其他文件由 Git 自身检查覆盖风险。
- “提交笔记修改”可编辑 commit 说明、选择文件。也可核对整个现有暂存区后明确提交；提交前再次校验暂存区，防止把后来暂存的文件混入。
- “历史与版本恢复”列出最近 150 个提交，并支持输入 tag、SHA 或分支。恢复前预览具体文件；恢复同步范围内的笔记并生成新提交，保留原有历史和范围外文件，不使用 `reset --hard`。不覆盖尚未提交的笔记修改。
- Git 冲突可比较当前分支、传入分支和工作区内容，采用某一方或手动编辑后标记解决。处理前会备份工作区及双方内容到实际 Git 元数据目录的 `vault-bridge-backups/`。文件冲突解决后，核对并选择“完成合并并同步”，继续推送到上游；其他复杂 Git 操作可使用终端。
- “Git 命令行 / Shell”支持以参数形式执行 Git 命令，例如 `git status --short --branch`。需要管道、重定向或完整 Shell 时，可在当前仓库打开系统终端。

只接收更新模式不会自动提交或推送，并禁用插件中修改仓库的管理操作。Git 管理入口和相应命令在没有本地 Git 仓库时隐藏。

桌面和手机要同步同一份内容，手机 API 配置需指向桌面 Git 的同一个远端仓库及分支；插件不自动改写其他设备的配置。运行中的原生 Git 操作遵循 Git 工作区机制，请在操作完成后继续编辑文件。自动提交可能使用现有 Git hooks 和签名配置；凭据或签名不可用时会报错并保留工作区。

## 日常操作

- 点击侧栏 Git 图标或桌面状态栏，打开同步菜单：立即同步、状态、预览计划、冲突处理、本机恢复版本、暂停 / 恢复自动同步、同步设置。打开菜单不会触发同步。
- 暂停自动同步会保存到当前设备，取消待执行的自动请求；仍可手动同步。恢复后会检查更新，停止编辑的等待时间保持原设置。进行中的操作完成前，菜单会禁用重复操作。
- 手机可通过命令面板搜索 `Vault GitHub Bridge`，选择“打开同步菜单”“立即同步”“查看同步状态”“处理同步冲突”或“查看本机恢复版本”。
- **打开 Obsidian 后同步**：默认开启，笔记库加载完成后同步一次，独立于编辑和定时自动同步。离线或在后台时，联网并返回前台后执行；操作忙碌时排队。首次连接仍需预览确认。可在同步设置中关闭；旧版本升级后默认开启。
- 自动同步开启后：**Cmd+S / Ctrl+S 保存完成即排队同步**；如果已有同步在运行，完成后再补传一次。插件不接管原生保存快捷键。限流时仍等待额度恢复。
- 普通输入：停止编辑 **10 秒**后自动同步，继续输入重新计时；Obsidian 自己的自动保存不延后这个计时。设置项“停止编辑后同步（秒）”可调 3～300 秒。
- 远端检查：默认每 90 秒检查其他设备更新，返回前台时也检查。启动同步由“打开 Obsidian 后同步”独立控制。失败后退避重试，并尊重 GitHub 限流；待上传批次会继续处理。
- 每批最多上传 25 个文件操作。初次导入较大的笔记库需要多轮；自动同步开启时后续轮次继续，手动模式可以再次点击同步。
- 正在聚焦编辑的 Markdown 文件会延后接收远端修改。切换到另一篇笔记或离开编辑器后，再同步即可。
- “只接收 GitHub 更新”不会上传本地文件；本地和远端同时变化仍显示冲突。

## 冲突与恢复（API 模式）

每个文件独立比较上次同步版本、本地版本、GitHub 版本，不使用修改时间判定胜负。

- 不同文件的修改自动汇总。
- 同一文件双方修改时，保留基线、本地和远端快照，在冲突面板查看三方内容。
- 可以保留本地、保留 GitHub，或“保留两份，继续同步”。保留两份会先把本地内容另存到 `GitHub 冲突副本/`，再采用 GitHub 版本；多项冲突可以批量处理，后续两份都会同步。
- 可以先在 Obsidian 中手动合并笔记，重新同步得到最新冲突后，选择保留本地。第一版不自动合并段落。
- 删除与另一端修改同时发生时，作为冲突处理；新设备空目录不会被当成删除。
- 单轮删除达到 10 项，或至少 3 项且超过已跟踪文件的一半，会暂停该轮，在“预览同步计划”列出将从本机或 GitHub 删除的具体文件。确认只授权当时核对的版本，分批处理时无需重复确认；额外删除或新内容不会被旧确认覆盖。
- 恢复面板显示当前仓库连接最近 200 条本机版本记录。恢复会另存到 `GitHub 恢复副本/`，不覆盖当前笔记。GitHub 的完整提交历史仍可在仓库网页查看。
- 上传采用 `force: false` 分支更新。其他设备先提交时，重新比较后重试，最多三次；不会强推。
- 远端分支读取绕过缓存。如果首次祖先关系检查异常，会重新读取复核；仍不一致才暂停同步。先保留本地笔记和恢复文件，再核对其他 Git 客户端是否重写了历史，不通过强推解决。

## 同步范围与限制

- 支持 `.md`、`.canvas`、`.base`、`.png`、`.jpg`、`.jpeg`、`.gif`、`.webp`、`.svg`、`.pdf`。
- 默认单文件上限 10 MB，可调 1～20 MB。超限会停止当轮同步，避免把未读取内容误判成删除。可按文件夹排除大文件。
- 隐藏路径、Obsidian 实际配置目录始终排除；不上传插件设置、凭据、工作区布局与缓存。
- 扫描中已列出但暂时无法读取的文件会停止当轮同步，不会把云盘尚未下载的文件误判成删除。
- 排除规则为文件夹前缀，一行一条，不使用 glob。改变仓库、分支或同步范围后，需要为新连接重新预览并确认；本地旧状态与恢复副本保留。
- 文件名须兼容 Windows/macOS；大小写冲突、路径穿越、Windows 保留名字、非 NFC 路径会停止同步并说明原因。符号链接、Git LFS、子模块暂不支持。
- iOS / iPadOS 会挂起后台应用。关闭 Obsidian 后不保证继续同步，应在离开前确认状态；待上传内容仍保存在本地。
- Markdown 更新使用 `Vault.process` 检查并发修改。Obsidian 没有二进制文件更新 / 删除的原子比较接口：附件和删除操作保留前一版本并在写入前复核，但不要同时用外部程序原地编辑同一附件。
- API 请求依赖设备能正常访问 `api.github.com`。GitHub 的写入限流可能让大型首次导入花费较长时间。
- 本机内容缓存目前不自动垃圾回收；频繁更新大附件会增加本地占用。不要随意删除插件的 `local/` 文件夹，否则会丢失恢复记录和同步基线。

## 本地状态（API 模式）

状态位于实际配置目录下：

```text
.obsidian/plugins/vault-github-bridge/local/<连接标识>/
  state-0.json
  state-1.json
  objects/<哈希前两位>/<Git blob SHA>
```

两份交替检查点带校验，记录已确认基线、冲突、恢复历史与未完成事务。覆盖前先保存内容对象；上传成功但响应丢失时，下次根据提交祖先关系确认是否已经发布。最新检查点损坏时读取上一份；两份均损坏时停止同步，不会静默清空基线。

这些本地文件不包含 GitHub Token，也不会被本插件上传。停止使用插件前，可保留完整笔记库与该文件夹作为恢复副本。旧连接标识的目录不会自动删除。

## 构建与验证

需要 Node.js 22+ 和 npm：

```bash
npm ci
npm test
npm run build
node scripts/smoke.mjs
node scripts/desktop-smoke.mjs
npm run package
```

构建文件在 `dist/`。安装包、源码包与 SHA-256 校验文件在 `release/`。自动化测试与真实 GitHub 隔离验证记录见 [TEST_REPORT.md](TEST_REPORT.md)。尚未完成真实 Obsidian 多端端到端验证，不能据此推断已在所有设备测试通过。

## 插件更新与发布

插件源码使用独立仓库。发布时把 `manifest.json` 的版本与 GitHub Release Tag 对齐（例如 `0.1.0`），上传构建后的 `main.js`、`manifest.json`、`styles.css`。后续可以申请社区插件上架，或用 BRAT 管理测试版。不要通过笔记同步覆盖运行中的插件程序。
